## 4. Adversarial Stress-Testing & Technical Critic Analysis

As an adversarial critic, I tested the assumptions, edge cases, failure modes, and boundaries of the proposals:

### 4.1 Challenge 1: EXIF Header Slicing Boundary in Camera RAW & Complex TIFFs
- **Assumption Challenged**: Slicing the first 128 KB (`file.slice(0, 131072)`) is sufficient to extract all EXIF/XMP tags across all image formats.
- **Attack Scenario / Edge Case**: Certain modern camera RAW formats (such as Sony `.ARW`, Canon `.CR3` with large embedded preview boxes, or TIFF files with IFDs at the end of the file) may position their metadata IFD offsets beyond the 128 KB mark.
- **Blast Radius**: `ExifReader.load(buffer)` would throw an error or return empty metadata for those specific RAW files.
- **Mitigation & Recommended Implementation Refinement**:
  - Implement a two-tier progressive slice: Start with 128 KB. If `ExifReader` indicates an incomplete IFD pointer or fails on a RAW format, expand the slice to 512 KB or 1 MB before falling back to filesystem dates.

### 4.2 Challenge 2: LSB Spatial Steganography Resilience Under Lossy Re-Compression
- **Assumption Challenged**: Spatial LSB (Least Significant Bit) modulation in the blue channel survives screenshots and unauthorized client leaks.
- **Attack Scenario / Edge Case**: If a client screenshots a watermarked proof and saves it as a lossy JPEG (or uploads it to Instagram/Twitter, which re-compresses images via lossy DCT quantization), the least significant bits are often smoothed out and discarded by the compression algorithm.
- **Blast Radius**: The invisible watermark extraction would fail on heavily re-compressed JPEG screenshots.
- **Mitigation & Recommended Implementation Refinement**:
  - The feature is fully effective for uncompressed formats (lossless PNG proofs, vector PDFs, original uncompressed screenshots, and local file disputes).
  - For future iterations targeting social media leak detection, supplement spatial LSB with a frequency-domain Discrete Cosine Transform (DCT) watermark or a discrete geometric corner micro-pattern that survives JPEG quantization.

### 4.3 Challenge 3: Standalone HTML Proofing Portal Memory Scaling on 500+ Photo Shoots
- **Assumption Challenged**: Inlining WebP base64 thumbnails into a single `.html` file is universally portable across all devices.
- **Attack Scenario / Edge Case**: While 100–150 photos at 480px WebP (~40 KB each) produce a lean 6–8 MB HTML file, an extreme user exporting 1,000 photos would generate a 50+ MB HTML file. Opening a 50 MB HTML file with 1,000 inlined base64 images on an older iPad or mobile browser could trigger Mobile Safari memory limits.
- **Blast Radius**: Mobile browser tab crash on massive shoots (>500 photos).
- **Mitigation & Recommended Implementation Refinement**:
  - Add a soft recommendation/warning in the Export Drawer if photo count exceeds 250 in HTML export mode.
  - Implement lazy image decoding in the HTML portal template (which is already included via `loading="lazy"` in `htmlPortalExporter.ts`).

### 4.4 Challenge 4: Linear Partition Aspect Ratio Clamping for Extreme Panoramas
- **Assumption Challenged**: Linear partition handles arbitrary aspect ratios smoothly.
- **Attack Scenario / Edge Case**: If a shoot contains a 5:1 panorama alongside 2:3 vertical portraits, the dynamic programming partition might assign the panorama to a row where its sheer width forces the computed row height to shrink drastically, making adjacent vertical photos appear tiny.
- **Blast Radius**: Uneven row heights in mixed-ratio mosaic sheets containing extreme aspect ratios.
- **Mitigation & Recommended Implementation Refinement**:
  - In `mosaicEngine.ts`, clamp the effective aspect ratio weights used for row height calculations between `0.5` (max vertical) and `2.5` (max horizontal) to preserve visual balance.
